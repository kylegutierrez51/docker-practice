INTRO

Container - package app with all necessary dependencies and configuration

Containers live in a container repo (private/public -- DockerHub), a special type of storage for them

Before Containers:
 - My laptop would have to install an exact PostgreSQL version for it to access the Runner

After Containers:
 - The container is its own isolated OS layer, so you can get the specific version of PostgreSQL
 - Run one command to fetch the container and start it, installing the app
 - Run same application with 2 different versions (e.g. Run Deplo on PC and Laptop, both on different branches/commits)

CONTAINERS

Made up of images -- layers of stacked images on top of each other

Bottom to Top:
 - Base Image: Provides OS (mostly Linux since it's small), Runtime env, or initial tools app needs to run
 - Intermediate images that lead up to Application Image
 - Application image - everything needed to run an app (app code, runtime env, dependencies, configs)


When you do a command like: 'docker run postgres:9.6':
 - It'll take less time if you already have a different version of Postgre since it only downloads layers that actually changed. 
 - Layers that stay the same do not redownload.


2 terms:
 - Docker Image: 
     - the actual package (config, postgres version, start script)
     - artifact that is movable

 - Docker Container:
     - Pull docker image on local machine
     - Starts the application
     - Creates container environment
     - Port binded to it that talks to app (Postgres, Redis, MongoDB, etc.) running inside of a container

  If it's not running, it's a Docker Image -- an atrtifact lying around
  If you start and run it on machine, it is a Docker Container

DOCKER VS. VIRTUAL MACHINE

OS kernel - separates applications from hardware, communicates with both.
 - Applications run on kernel layer

Docker and VMs are both virtualization tools

Docker - virtualizes the application layer. Docker image contains app layer of OS and some other apps installed on top of it and uses kernel of host 

VM - Has application layers and its own kernel, so it virtualizes the complete OS. 
 - When you download a VM image on your host, it uses its own kernel host.

Docker Images:
 - Smaller (couple of MBs)
 - Docker containers start and run much faster
 - Compatibility: May not be able to run on any other host (e.g. Run Linux-based Docker Image on a Windows host -- may not be compatible with Windows kernel)
         - Workaround: Docker Toolbox - abstracts kernel to make it possible for your OS host to run different Docker images

VM images 
 - Bigger (couple of GBs)
 - Much slower, they have to put OS kernel and applications ontop of it
 - Compatibility: VM of any OS can run on any other OS host

COMMANDS

docker pull <image>:<tag> - Downloads container image to local machine
 -- e.g. docker pull redis:5.0.6


docker images - shows each image's details



docker run <image>:<tag> - creates and starts new container from docker image
 - if requested image is not found locally, Docker pulls it from a remote registry (Docker Hub) before running it

 - docker run redis:4.0 - 'docker pull' and 'docker start' in one command, pulls specific redis version and starts it

 - options (put before <image>): -d (detached mode), -p[HOSTPORT:CONTAINERPORT], --name [name]

 - 'tag' can be set to 'latest'



docker ps - lists running containers
 - docker ps -a  -- lists both running and stopped containers


docker [start/stop] <container_id> - starts/stops container



Detached Mode: Runs a container in the background of your terminal, so it executes but doesn't output anything in the current terminal except the Container ID
 - Purpose is so that you can continue typing other commands in the same terminal



If you run 2 versions of Redis from separate containers at the same, even if they both use port 6379, it doesn't conflict if they use different OS host ports
 - 2 containers can listen on the same Port AS LONG as you bind them to 2 different ports on your host machine.
  - Ex: Container 1 and 2 listen on Port 3000, but on our OS host, Container 1 is on 3000 and Container 2 is on 3001.

    This means you have to make a binding between your PC's port and your Container's port.

            To do that: 
                1. docker run -p3000:6379 redis
                    - 3000 -> port of the host
                    - 6379 -> container port that you're binding to host port (6379 -> 3000)
                
                2. docker run -p3001:6379 redis:4.0
                   - If you did: docker run -p 3000:6379 redis:4.0 then docker sends an error
                
                docker ps - shows the binding

DOCKERS IN SOFTWARE DEV

Docker Network - isolated network where containers run in.
 - When you deploy 2 containers in same Docker Network, they can talk to each other JUST by using the container name (no port, localhost, etc.)

In the app, node.js (runs outside Docker Network) connects to those containers from outside (from your OS host) using localhost and port number.



docker network ls

docker network create <name>



Setup:
    mongo:
        docker run -d -p 27017:27017 -e MONGO_INITDB_ROOT_USERNAME=mongoadmin -e MONGO_INITDB_ROOT_PASSWORD=secret. --name mongodb --net mongo-network mongo

    mongo-express:
        docker run -d \
            -p 8081:8081 \
            -e ME_CONFIG_MONGODB_ADMINUSERNAME=mongodb \
            -e ME_CONFIG_MONGODB_ADMINPASSWORD=secret \
            --net mongo-network \
            --name mongo-express \
            -e ME_CONFIG_MONGODB_SERVER=mongodb \
            mongo-express

        docker run -d -p8081:8081 -e ME_CONFIG_MONGODB_ADMINUSERNAME=mongoadmin -e ME_CONFIG_MONGODB_ADMINPASSWORD=secret. --net mongo-network --name mongo-express -e ME_CONFIG_MONGODB_SERVER=mongodb mongo-express 


            the network has to be 'mongo-network', matching that of the created docker newtwork 'mongo-network' (docker network create mongo-network) so that mongo-express and mongodb can communicate

            also, ADMIN[USERNAME/PASSWORD] are same as MONGO_INITDB_ROOT_[USERNAME/PASSWORD]

            

on localhost:8081, login using ME_CONFIG_BASICAUTH_[USERNAME/PASSWORD] -- (admin, pass)

The ADMIN[USERNAME/PASSWORD] are used internally by mongo-express to talk to the mongo container.

DOCKER COMPOSE 

Annoying:
        docker run -d \
            -p 8081:8081 \
            -e ME_CONFIG_MONGODB_ADMINUSERNAME=mongodb \
            -e ME_CONFIG_MONGODB_ADMINPASSWORD=secret \
            --net mongo-network \
            --name mongo-express \
            -e ME_CONFIG_MONGODB_SERVER=mongodb \
            mongo-express

Better:
    A docker-compose.yaml file that can run those commands for you

    Networks (docker network create <name>) takes care of creating a common Network, so it doesn't have to be specified in docker-compose.yaml


docker-compose -f docker-compose.yaml up
        -f : file
        up: start all containers in .yaml

        
        this created a network called 'docker-practice_default' and ran the 2 containers ('docker-practice-mongodb-1', 'docker-practice-mongo-express-1)

        you can do: 'docker network ls' to see the new network


        Once the command runs, logs of both containers mix since they start at the same time


In Docker Compose, if one container depends on another one, you can configure waiting logic


When you restart a container, everything you configure in that container's application is gone
 - No data persistence in containers
 - Use docker volumes for data persistence



docker-compose down -v
    stops and removes all containers in .yaml AND the created network

    -v : deletes named volume, meaning data in mongo container is lost 
          - useful if, for ex, you run docker-compose.yaml and realize you forgot to set up the env variables from .env properly

    the next time you run 'docker-compose up', it recreates the network 


    If you ran docker-compose.yaml with volumes and attempt to comment out the volumes to delete data, it won't work since docker-compose up copies over volumes from old container instances.

    to remove a volume (excluding -v as that won't work if the volumes were commented out):

    docker compose down
    docker volume rm <name>

DOCKERFILE

Blueprint for creating docker images

Process:
    1. Create a docker image via Dockerfile (docker build -t <image_name>)
    2. Create the container for that image (docker run <image_name>)


The first line is:
'FROM <image>'


"RUN mkdir -p /home/app" -- execute linux commands
    This directory is created INSIDE of the container
    executes in the CONTAINER

"COPY ./app /home/app" 
    copy files you have on your OS Host (in ./app) inside this image (into /home/app)
    executes on the HOST machine
    

CMD ["node", "server.js"]
    Executes an entrypoint Linux command
    this translates to "node server.js"
    Allows for multiple RUN commands


Hardcoding 'ENV' credentials into Dockerfile is unsafe since anything set with it gets baked into the image layers permanently, so anyone who gets access to the Docker image can see them easily.

just inject the .env vars at buildtime instead:
        docker build -t my-app .
        docker run --env-file .env -p 3000:3000 my-app


docker build -t <name>:<tag> .

    -t gives a name and tag
    . - location of Dockerfile. Since we're in the same directory as the dockerfile, use "."


        docker build -t my-app:1.0 .


When you readjust Dockerfile, you MUST rebuild the image.


to remove and rebuild the Dockerfile:

docker stop <container_id>
docker rm <container_id>
docker rmi <container_id> -- removes the image
docker images -- view the images
docker build -t <name>:<tag> .


docker exec -it <container_id> /bin/sh 
    shows current logs for that container

PRIVATE DOCKER REGISTRY (REPOSITORY)

Amazon ECR - Store different tags (versions) of the same image


to push an image into a private repo:
 1. login to that private repo to authenticate yourself (docker login <command>)
        - the 'command' is given by AWS ECR, and requires AWS CLI installed and credentials configured for it

 2. docker build -t <name>:<tag>

 3. tag the image, so that it can be pushed to AWS ECR
       - docker tag <local_image>:<local_image_tag> registryDomain/<remote_image>:<remote_image_tag>

       'docker tag' creates a new reference to an existing Docker Image.
       It's used here to match the image in AWS ECR, so that we can push it there easily
        then do 'docker images' to see the image

 4. docker push registryDomain/<image>:<tag>




Image Naming in Docker registries:

        'registryDomain/imageName:tag'

        registryDomain - host, port, etc.


        When we pull an image out of DockerHub (docker pull), we are able to pull an image with a shorthand, which is why 'registryDomain' doesn't show

         - In Docker, when we do: 'docker pull mongo:4.2' (or docker push mongo:4.2)
            - it's equal to 'docker pull docker.io/library/mongo:4.2', where 'docker.io/library' is the domainRegistry

            - It assumes we are pulling (or pushing) from DockerHub

         - In AWS ECR, you have to include the full domainRegistry, which is a really long string.



If you make changes to your Dockerfile or code inside container and update it on AWS ECR:
 1. Rebuild image -- docker build -t <image>:<tag>

 2. Create new reference to that built image in step 1 -- docker tag <local_image>:<local_image_tag> registryDomain/<remote_image>:<remote_image_tag>

 3. docker push registryDomain/<image>:<tag>





Process:
 1. Get Image from DockerHub 
 2. commit docker-compose.yaml and Dockerfile to Git
 3. Jenkins or GitHub Actions CI pushes them to Docker Repo (AWS ECR)
 4. Pull the image from AWS ECR to use in dev server

DOCKER VOLUMES

Data persistence. 
When you stop/restart a container, the data in the virtual file system of the container gets deleted.

Host - Physical File System
Volumes plug the physical file system path (folder/directory) and plug it into the container's virtual file system path



3 Volume Types:

1. Host/bind Volumes

    'docker run -v /home/mount/data:/var/lib/mysql/data

    '/home/mount/data' -- host volume : you decide where on the host file system the reference is made
    '/var/lib/mysql/data' -- container volume


2. Anonymous Volumes - no reference to container directory

    'docker run -v /var/lib/mysql/data' 

    creates a volume just by referencing the container directory. No host directory specified -- Docker takes care of it.

    Docker creates the volume with a random hash as its name, so it can be easy to lose track of.


3. Named Volumes - specifies name of the folder on the host file system -- FIXES issue with anonymous volumes

    'docker run -v name:/var/lib/mysql/data'

    Unlike anonymous volumes, you can reference the volume by name, without knowing the path

    !! These are the ones you should be using in production


A named/anonymous volume can be declared by the image itself (via VOLUME in Dockerfile)




docker-compose.yaml:

            mongodb:
                image: mongo
                ports:
                  - 27017:27017
                environment:
                  - MONGO_INITDB_ROOT_USERNAME=${MONGODB_USERNAME}
                  - MONGO_INITDB_ROOT_PASSWORD=${MONGODB_PASSWORD}
                volumes:
                  - mongo-data:/data/db



            volumes:
                mongo-data:
                    driver: local


'mongo-data' is the volume name 
'data/db' is the path inside the mongo container where MongoDB stores its database files


even if these 2 lines:
        volumes:
            - mongo-data:/data/db

werern't there, Mongo's container would still end up with a volume mounted at /data/db as an anonymous volume Docker generates automatically with a random hash name. 

The benefit of having those 2 lines is that you can control the name of the volume (docker volume inspect docker-practice_mongo-data) instead of getting a random anonymous one



Volume Location:
On Windows:
 - C:/ProgramData/docker/volumes -- native Windows containers

Docker Desktop runs a hidden Linux VM (WSL2 by default) that keeps the Docker daemon and volumes inside that VM's virtual disk
 - Since mongo, mongo-express, and node:13-alpine are Linux images, the path is '/var/lib/docker/volumes/...' inside the VM.
 - To access it (on WSL2 backend, which is the default in Docker Desktop):

            Open a terminal into Docker's own WSL distry and browse via these commands:

            wsl -d docker-desktop
            ls /var/lib/docker/volumes/docker-practice_mongo-data/_data

EXTRAS

Sequence:

 1. Start Docker Desktop
 2. Confirm no leftover strandalone containers are holding ports you'll need

        docker ps -a
        docker rm -f mongodb mongo-express   # only if these standalone ones still exist

 3. docker-compose --build 

        builds 'my-app' from Dockerfile, pulls mongo/mongo-express, and starts all 3 on an auto-created network (docker-practice_default) so mongodb resolves by service name exactly as mongoUrlDocker in server.js expects

        Equivalent to:
            docker build -t docker-practice-my-app .
            docker-compose up

        Subsequent 'docker-compose up' (w/ no --build) will reuse the cached image and won't pick up changes to Dockerfile, app/server.js, etc. 
          -- You'd need to rerun 'docker build -t docker-practice-my-app' or use 'docker-compose up --build'

        
 4. Verify the app (port 3000) and mongo-express UI (8080 -- login: admin / pass)

 5. Shutdown: docker-compose down 

        Add -v if you want to wipe the mongo-data volume too







docker-compose.yaml:

  my-app:
    build: .
    ports:
      - 3000:3000
    env_file:
      - .env
    depends_on:
      - mongodb


my-app: declares a service named 'my-app' 

build: . -- instead of pulling a pre-built image (like mongo and mongo-express), build the image from a Dockerfile in this directory (docker-compose.yaml and Dockerfile are in same directory)

ports: - 3000:3000 -- publishes container port to host port 3000, so https://localhost:3000 on Windows machine reaches it.

env_file: - .env -- loads every KEY=value line from the root.env file directly into the container's env variables
 - This populates 'process.env' in server.js

depends_on: - mongodb -- tells compose to start the 'mongodb' container before starting 'my-app'
 - this waits for the container process to launch, not for Mongo to finish initializing and accepting connections
 - This means if you go to port 3000, you'll see 'ECONNREFUSED' initially
